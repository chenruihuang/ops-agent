## 简历正文（可直接粘贴）

**项目名称**：运维知识助手 —— 企业级多知识库 Agent 平台（个人项目）

**技术栈**：Python、LangGraph、FastAPI、MCP、Redis（RediSearch）、Qdrant、Prometheus、Grafana、Docker Compose、nginx、SSE、pytest、Java Spring Boot（MCP 仿真宿主）

**项目描述**：面向运维场景的企业级 Agent 平台，覆盖知识问答、实时数据查询、复合诉求处理与写操作人工确认四大场景。基于 LangGraph 实现 13 节点状态编排（缓存分段、并行扇出、4 类终局），BM25+稠密向量双路召回 RRF 融合，两级语义缓存与单飞并发去重，熔断-重试-双维降级的韧性内核，通过 MCP 协议接入 Java 仿真工具宿主（读类工具数据来自台账快照、写类工具为模拟执行）；SSE 全事件流 + Prometheus/Grafana 全链路可观测，故障演练脚本化。196 项测试、710 条断言全离线可回归。

**核心职责与项目成果**：

**1. LangGraph 多分支编排与并行架构**  
设计「路由 → 记忆加载 → 精确缓存 →（未命中）向量化 → 语义缓存 → 单飞 → 分叉（工具∥召回）→ 汇合 → 生成/挂起」的 13 节点状态图：工具调用与知识召回两路并行（墙钟取 max 而非相加），条件判定收敛在汇合节点之后，四类终局（闲聊/缓存命中/流式生成/挂起待确认）。196 项 pytest、710 条 check 断言 19 秒全离线跑完，覆盖路由、编排、缓存、沙箱等核心场景。**性能优化**：定位并修复「exact 缓存命中也要先付 BGE 编码（stage p50 6.33s）」的架构瓶颈——把缓存查询拆成 exact/semantic 两段，命中路径零编码，同机实测命中 TTFT 从 ≈未命中（P50 6668ms）降到 21–26ms。

**2. 混合检索与消融评估**  
BM25 稀疏检索 + BGE 稠密向量检索双路召回 + RRF 融合 + 重排。52 题标注集上配置可消融、结果可回归：BM25 单路 context_recall@5 0.865 / 向量单路 0.875（hit_rate@5 0.958，覆盖主要来自向量路）→ RRF 融合 0.896 → 加重排 0.920，hit_rate@5 0.979、MRR 0.887，召回段 p50 238.8ms。评估脚本复用线上同一召回实现（仅注入配置差异），杜绝「评估自建检索」导致的口径分裂。

**3. 两级缓存与单飞并发去重**  
exact 精确缓存（键含知识库版本号，**命中零编码、TTFT 毫秒级**）→ 语义缓存（KNN + 实体护栏，拦截"向量相近但答案不同"的误命中；编码只由未命中请求支付，结果与向量召回共用）→ singleflight 并发去重（Redis SET NX 锁，leader 唯一计算、follower 回放结果，最多等待 6s 自行兜底）。知识库版本 bump 后旧答案全副本自然失效，无需逐条清理。

**4. 三层记忆与优雅降级**  
本轮请求状态 / 会话历史（Redis list 滑窗）/ 长期事实（hash + TTL + 条数上限）三层记忆。Redis 完全宕机时问答照常：加载返回空上下文、写入返回错误串并转成可见的降级事件——锦上添花的依赖不拖垮主链路，但降级对用户可见、对指标可归因。

**5. 写操作安全沙箱**  
写类工具统一过闸门：策略判定（参数与值白名单 + 禁改清单）→ 挂起并签发一次性凭据（Redis GETDEL 原子消费、600s 过期、跨会话拒用）→ 确认后仅从存储快照读取参数执行（「确认了 A 却执行 B」在结构上不可能）→ 全程审计落盘 + 决策指标。复合诉求（既要执行又要提问）按分句判定知识归属，写操作不因知识问句被静默吞掉。

**6. 韧性内核与故障演练**  
熔断在外、重试在内（白名单只重试瞬态/超时/连接/5xx）；纵向降级（同一工具 MCP → 缓存 → mock）+ 横向降级（skill 步骤声明式 fallback）。故障演练脚本化：Java 侧故障注入头 + 探针 + 自动报告，10 轮注入下请求成功率 100%；Qdrant 停机检测 0.55s、MTTR 27.9s；Redis 停机端到端恢复 162s——期间功能降级、服务不中断。

**7. 全链路可观测**  
SSE 定义 10 类事件的帧协议（meta 首帧、done 收尾、终止符、15s 保活注释帧），请求 → 节点 → token 全程 trace 分段计时（TTFT 单点测量）；Prometheus 20+ 业务指标 + Grafana 31 面板由脚本生成，11 条守门测试防「指标名写错画空线」「面板假死」「空值误渲染」。定位并修复 nginx upstream 静态解析导致的**假负载均衡**（扩容后 1561 条请求全落单副本）——resolver 内嵌 DNS 5s 重解析 + 变量 proxy_pass。

**8. MCP 标准化接入（仿真业务环境）**  
Spring Boot 实现 MCP 仿真宿主（5 个运维工具，JSON-RPC over HTTP）：读类工具数据来自打包进 jar 的台账快照（工单/资产/告警，对应真实系统「资产台账 DB / 工单系统 API」的位置），写类工具为模拟执行（返回执行回执、不触碰真实服务）；宿主为自洽独立服务，不依赖 Python 侧目录挂载。Python 侧 mock 与 MCP 服务同签名（结构保证降级行为一致），支持故障注入头供演练使用，19 条探针自检覆盖正常 / 熔断 / 注入场景。

### 数字背后的四个口径红线（面试必被追问）

1. **"成功率 100%" 不是可用性 SLA**——它是"故障注入窗口内探测请求的成功率"，含义是"降级路径让请求没有失败"，不是"服务可用性 99.9x%"。主动说清这一点比被戳穿强得多。
2. **路由 100% 要带限定语**——52 题里 45 题是 rag，全判 rag 的基线准确率就有 86.5%。所以正确说法是"52 条标注全对，且非 rag 题（tool/hybrid/chitchat）召回 7/7"。只写"100%"会被当成不懂不平衡评估。
3. **检索 0.92 和答案侧 0.88 是两套指标**——前者是离线检索评估（context_recall@5，文档级），后者是走完整生成链路的答案侧评估。数字不同不是矛盾，是测量层级不同；面试时主动区分会加分。
4. **数据是仿真的，主动说**——MCP 宿主的数据源是打包进 jar 的台账快照，写类工具是模拟执行（`simulated=true`）。这不减分：项目重点在 MCP 协议接入、故障注入、降级链路，这些在仿真环境上完全成立；藏着掖着被问"接的哪家生产系统"才减分。正确姿势是把它讲成契约先行：接口、协议、故障注入面都按真实系统的位置留好了，换数据源只动 Repository 一层。

## 面试素材一：项目里遇到的问题 → 解决方案 → 指标变化

> 每条都是真实发生、有代码与数据佐证的。讲法建议：先讲**症状**（"有数但数错了"），再讲定位，最后讲修法与效果——比"我做了 XX 优化"可信得多。

**1. 假降级：配置状态伪装成故障**

- **症状**：关闭重排（`RERANK_ENABLED=false`）后，每个未命中请求都发一条 `degraded` 帧，监控上"降级数"恒等于"缓存 miss 数"（72=72）——降级信号完全失去信息量。
- **定位**：配置项缺失被当成了运行时故障。降级的定义本身就是设计决策：**只有真故障才配得上 degraded 信号**。
- **修法**：配置类状态改发 `notice{code:rerank_disabled}`（不打断、可解释），`degraded` 只保留真故障（异常/超时/连接失败）。
- **效果**：降级信号从"每次 miss 一条噪音"变为零假阳性；此后故障演练里 `degraded(stage)` 每一条都对应真实故障，可归因。
- **面试金句**：这是"有数但数错了"最隐蔽的一种——不是没监控，而是监控在说谎。

**2. 假负载均衡：nginx upstream 静态解析**

- **症状**：`--scale api=2` 扩到 2 副本后，压测 50 分钟 1561 条请求**全部**落在同一个副本，另一副本业务指标为零——扩容完全是摆设。
- **定位**：nginx 对 upstream 主机名只在启动时解析一次，副本重建换 IP 后缓存指向失效。
- **修法**：`resolver 127.0.0.11 valid=5s`（Docker 内嵌 DNS）+ 变量 `proxy_pass`，每 5s 重新解析。
- **效果**：扩缩容后两副本 `chat_requests_total` 都有增长序列，Prometheus 一眼可验证。

**3. 缓存命中的优势被编码吃干（已写进简历正文第 1 条）**

- **症状**：压测发现 TTFT[hot] P50 6668ms ≈ TTFT[cold] 6425ms——缓存命中"首字快"的卖点完全不存在。
- **定位**：stage 计时显示 `embed_query` p50 6.33s，而它排在缓存查询**之前**——exact 命中也要先付一次 BGE 编码。
- **修法**：缓存拆成 `cache_exact →（未命中）→ embed → cache_semantic` 两段；exact 查询只是 Redis GET，命中请求不进 CPU 队列；编码只由未命中支付，结果供语义缓存与向量召回共用。
- **效果**：同机实测 exact 命中 TTFT **21–26ms**（此前 ≈未命中）；trace 中命中请求无 `embed` 段；守护测试钉住"exact 命中不调编码"，防止回退。
- **讲法要点**：主动说清"绝对毫秒数不可跨环境引用（共享 vCPU 漂 7 倍），只报同机相对差异"——这句本身就是加分项。

**4. 评估与线上口径分裂（结构性防御）**

- **风险**：评估脚本最容易自己另写一套检索逻辑，跑出漂亮数字但与线上行为无关。
- **修法**：评估脚本强制复用线上同一召回实现（只注入配置差异），并加守护测试 `test_eval_calls_serving_recall`——谁在评估里自建检索，测试直接红。
- **效果**：检索消融（BM25 0.865 / 向量 0.875 → RRF 0.896 → 重排 0.920）与线上行为同源，数字可直接引用。

**5. 空闲时"成功率 0%"：0/0 被 clamp 成 0**

- **症状**：无流量时段大盘显示请求成功率 0%——看起来服务全挂，实际是没有请求。
- **定位**：分母为 0 时被 `clamp_min` 兜成了 0。"没有数据"和"数据为零"是两种状态，混在一起就是把"没流量"渲染成"全失败"。
- **修法**：比率类面板统一 `noValue` 处理；顶行先看近 5 分钟请求数（用 `chat_requests_total` 而非 `llm_requests_total`——后者缓存命中不计数，会误报"无流量"）。
- **效果**：大盘不再出现假性 0%；顺带修掉"命中率 75% 时顶行误报无流量"的连锁问题。

**6. 复合意图静默丢失写操作**

- **症状**："帮我重启 order-service，并查一下 oom 怎么办"——答案正常回答了 OOM，但**写操作没触发确认**，静默消失。
- **定位**：`RouteDecision` 的 hybrid 分支漏传 `needs_write` 字段（声明了从未赋值）；另发现"重启 X 的步骤是什么"这类**知识问句**会误触写操作。
- **修法**：hybrid 分支显式传 `needs_write=True`；引入**分句判定**——知识信号只在写动词同一分句内才否决写操作。
- **效果**：实测该问法 `route=hybrid`，`restart_service` 被沙箱拦截并签发确认凭据，知识部分照常回答（开头声明"尚未执行"）。
- **讲法要点**："静默丢失"比报错严重得多——用户以为执行了，实际没有。这类 bug 只能靠端到端用例（真实问法过全链路）抓，单元测试测不出来。

**7. 已定位未修（诚实讲，体现判断力）**

- trace 文件多副本并发 append 损坏：24,560 行中 682 行结构不完整；修法已定（`O_APPEND` 单次原子写 / 按副本分文件），未实施的原因是当前 trace 只用于本地回放，修复优先级低于功能项。
- 纯写挂起路径不释放单飞锁：影响有界（30s TTL 兜底），已记录。

## 面试素材二：工业级落地的提升点（主动提出，展示上限意识）

> 讲法：每条都按"项目现状 → 工业级做法 → 为什么现在没做"三段说，避免变成"我知道一堆名词"。

**1. 意图路由：从正则到可学习路由**

- 现状：纯正则规则（52 题标注集上可评估、可解释、零成本），刻意偏向多答知识（漏判 rag 可恢复，漏判 tool 静默丢答案）。
- 工业级：**规则兜底 + 模型主判的双层路由**——小模型（BERT-tiny 级分类器）或 LLM 结构化输出做主判，规则做低置信度回退与安全红线（写操作永远过规则）；标注集持续扩充，badcase 自动回流标注；路由决策本身打点（准确率/混淆矩阵随版本跟踪）。
- 为什么现在没做：流量没有积累到训练集规模；正则的可解释性在面试和排障时是资产不是负债。

**2. 熔断降级的全覆盖与多副本一致性**

- 现状：熔断只包 MCP 工具调用；LLM/Redis 靠 try-except 降级；breaker 状态每副本独立。
- 工业级：① LLM 加熔断 + 降级链（备用模型 → 缓存答案 → 繁忙文案），LLM 是 Agent 最核心依赖，它没熔断是最大缺口；② breaker 计数迁 Redis（Lua 原子更新），多副本一起跳闸——否则 N 副本把有效阈值放大 N 倍；③ **全请求级准入控制**：全局并发上限 + 超载 429 卸载（排队=每个请求都慢=雪崩放大）、重试预算（重试量 ≤ 流量 10%，防重试风暴）、超时预算逐级递减（deadline propagation）。
- 网关的角色：nginx 只做边缘粗滤（限流/被动摘除，开源版无主动探测与半开）；语义降级**永远留在应用层**——网关不知道"这个答案可以用缓存顶"。多服务阶段再考虑 Envoy（outlier detection + 连接级熔断下沉）或 LLM 专用网关（LiteLLM：per-model cooldown/fallback/成本看板）。

**3. 沙箱的企业级演进**

- 现状：服务白名单硬编码、审计落本地 jsonl、确认凭据在 Redis。
- 工业级：白名单来自 CMDB（服务与负责人单一来源）；审批接入企业 IM 卡片（企微/飞书），审批即工单、可追责；高危操作二次确认（双人复核）；审计接 SIEM。

**4. 知识库运营**

- 现状：全量入库、kb_version 整体推进、RAGAS 未正式跑。
- 工业级：增量入库 + 文档级版本；切片质量评估（召回差的 case 回溯到切片粒度）；RAGAS 答案侧评估正式化并进 CI 门禁；多租户隔离（kb_version 升级为 namespace）；文档级权限（检索前过滤，而非检索后删）。

**5. 可观测性补强**

- 现状：trace 本地 jsonl（多副本并发写损坏已定位未修）、慢故障无告警。
- 工业级：trace 按副本分文件或 O_APPEND 单次写，接 Langfuse/OTel 后端；**慢故障告警**（P95 持续越限触发，而非错误率——错误率告警需要持续流量才成立）；SLO 用错误预算管理而非"99.95%"拍脑袋。

**6. LLM 成本与供给治理**

- 现状：单供应商（DeepSeek）、无成本口径。
- 工业级：多供应商路由（主备切换按熔断状态自动决策）；token 成本按会话/意图聚合进大盘（`cache_tokens_saved` 已有，缺"花掉多少"那一侧）；按用户/租户限流配额。

**7. 安全**

- 现状：API Key 鉴权、写操作沙箱、参数白名单。
- 工业级：**prompt 注入防护**（检索到的文档内容是不可信输入——知识库被投毒即可劫持答案，需要指令/数据隔离与输出检测）；工具输出消毒（MCP 返回内容同样不可信）；密钥轮转与托管（项目 .env 曾泄露已轮转——可以主动讲这个教训）。

## 面试素材三：每项技术的选型原因与更好的替代方案

> 讲法建议：不要背表，挑 3–4 个能讲出"取舍依据"的展开（推荐：编排、缓存存储、熔断、路由）。
> 万能句式："当时约束是 X，所以选了 Y；Y 的代价是 Z，当 X 变化（流量/团队/规模）时，我会换成 W。"

| 技术 | 为什么选它（真实约束） | 更好的方案（什么条件下换） |
|---|---|---|
| **LangGraph**（编排） | 需要"条件边 + 并行扇出 + 人在环挂起恢复"三个能力同框架；状态显式（TypedDict），13 个节点可逐个离线测试——196 项测试全离线跑通就是靠它 | 流程变简单（纯线性）→ 直接 FastAPI 顺序调用，框架是负债；多 Agent 对话博弈场景 → AutoGen/CrewAI 更合适；**坚决不用 Dify/RAGFlow/FastGPT 当基座**：黑盒编排让"评估口径"不受控——本项目最核心的资产就是"每个数字能复现"，低代码平台做不到 |
| **FastAPI + SSE**（传输） | 单向推送 + 自动重连 + `EventSource` 原生支持；代理/网关兼容性比 WebSocket 好（nginx 只需关 buffering） | 需要客户端中途发消息（打断生成、补充参数）→ WebSocket 或 HTTP/2 双向流；本项目挂起轮用独立 `POST /chat/confirm` 补交互，SSE 够用 |
| **Redis + RediSearch**（缓存） | 一个组件同时承担：exact 缓存、语义缓存（HNSW KNN）、singleflight 锁、确认凭据、kb_version 元数据——运维面少一个组件；GETDEL/SET NX/Lua 都是现成原子原语 | 语义缓存规模大（百万级）或需要过滤语法更强 → Qdrant（本项目向量检索已在用，schema 一样，迁移成本可控）；Redis 语义索引需要 RediSearch 模块且锁 RESP2 协议（RESP3 下结构变化会静默 miss），这是真实运维成本 |
| **Qdrant**（向量库） | payload 过滤（kb_version 隔离新旧知识库）+ HNSW 调参直接；单二进制 Docker 部署轻 | 千万级+ 多租户 → Milvus；已重度使用 PostgreSQL → pgvector 省一个组件；依赖里同时装了 chromadb 是为了评估脚本横向对照后端，不是生产双栈 |
| **BM25 + 向量 + RRF**（召回） | 消融数据说话：BM25 0.865 / 向量 0.875 / RRF 0.896——两路覆盖面不同（BM25 精确匹配型号/编码，向量管同义改写），谁都不能去；bm25s 纯 NumPy 实现，离线测试零依赖 | 语料高度口语化、无编号实体 → 单路向量+重排足够；语料极大 → 加一层标量预过滤或 ColBERT 式 late-interaction；RRF 不需要调权重（k=60 固定），比加权融合好落地 |
| **bge-small-zh-v1.5**（embedding） | 中文优化、512 维小模型 CPU 可跑（个人项目无 GPU）；全离线测试因此可行 | **已知硬约束：输入上限 512 字符，超限静默截断**——长文档必须先切片；换 bge-m3（8192 长度）可解决但要同步改切片粒度与全部缓存 key（模型名在 key 里）；上 API embedding（OpenAI/智源）换延迟与质量，代价是离线测试体系失效 + 按量付费 |
| **bge-reranker-base**（重排） | 消融显示重排 recall@5 从 0.896 → 0.920，收益真实；CPU 推理可控（rerank_max_per_doc 限流防雪崩） | 预算允许 → Cohere Rerank / bge-reranker-v2-m3（效果更好，API 化）；重排收益被上下文预算吃掉时先放开预算再谈排序（本项目实测教训） |
| **自研熔断/重试**（不用 pybreaker/tenacity） | pybreaker 是同步 API，拿不到带 trace span 的调用上下文；tenacity 管不了"多次重试只算一次熔断失败信号"；时钟与 sleep 可注入，测试不用真等——韧性内核 100% 被离线测试覆盖 | 生产化首选**替别人维护的轮子**：resilience4j（Java 侧）、polly（.NET）、Python 生态确实没有异步熔断的成熟选项，这正是自研的辩护点；引入 Envoy 后流量层熔断下沉，应用层只留语义降级 |
| **正则意图路由**（不用模型） | 52 题标注集可评估、可解释、零成本零延迟；误判代价不对称（漏 rag 可恢复、漏 tool 静默丢答案），规则可以刻意偏向安全侧 | 流量积累后 → 小分类器（BERT-tiny）或 LLM 结构化输出主判 + 规则兜底（写操作永远过规则红线）；详见面试素材二第 1 条 |
| **DeepSeek**（LLM） | 中文运维语料表现好、API 便宜（个人项目成本约束）；OpenAI 兼容协议，换供应商只改 base_url | 需要更强推理 → 换大模型（协议同）；生产多供应商 → LiteLLM 网关做主备切换与成本看板——但**先给 LLM 调用加熔断**，换供应商解决不了"供应商挂了怎么办" |
| **Langfuse**（trace 云端） | 开源自托管、OTel 兼容；本地 jsonl 是全量事实源（可写断言），Langfuse 是采样上报的看板，两者分工明确 | 团队已用 Datadog/Tempo → 直接 OTel SDK 不必多接一家；注意现状缺口：LangGraph 节点是独立 asyncio task，OTEL contextvar 跨节点丢失，span 树是平的（父子关系记在 metadata 里） |
| **Docker Compose + nginx**（部署） | 单机全栈（api×2、java-mcp、redis、qdrant、prometheus、grafana、nginx）一条 `docker compose up` 拉起；nginx 做 TLS/限流/被动摘除够用 | 多机/自动伸缩 → k8s（但要付出双倍运维复杂度，个人项目不值）；服务间通信复杂后 → Envoy/Istio，熔断限流下沉 sidecar |
| **pytest 离线测试体系**（710 条 check） | 所有外部依赖（LLM/Redis/Qdrant/MCP）都可注入假实现且与真签名一致；`check()` 参与退出码、计数从数据派生——测试数字本身也可信 | 这条不建议换方案，建议讲**为什么 mock 可信**：假实现与真实现同签名、降级行为一致（mcp mock 与 Java 宿主同契约），且关键契约有真机探针二次验证（19 条 mcp_probe） |

**三个高频追问的展开**：

1. "为什么不用 Dify/LangChain 全家桶？"——编排选 LangGraph 而不是低代码平台的根本原因不是功能，是**评估口径**：本项目的检索消融、答案侧评估、故障演练全部要求数字可复现，黑盒平台里"为什么召回 5 片而不是 8 片"无法回答。（requirements 里有 langchain-core，只用于与 LangGraph 的消息类型兼容，编排本体没用 LangChain 链。）
2. "语义缓存为什么不直接用 GPTCache？"——GPTCache 的护栏是可配置相似度阈值一项；本项目的锚点一致性 + 长度比护栏是业务语义层（数字不同答案相反必须拦），写在自己可控的纯函数里，测试可穷举、指标可归因（`cache_guard_rejected_total` 按 reason 分桶）。
3. "这套架构哪个环节最先撑不住？"——**embedding 编码**：CPU 上 bge-small 是当前 TTFT 主导项（冷路径），流量上来后第一件事是 GPU 推理或 API 化 embedding，第二是 breaker 状态迁 Redis（多副本阈值放大 N 倍），第三才是换向量库。把"扩容顺序"讲清楚比列组件名更能体现容量意识。
